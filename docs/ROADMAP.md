## Phase 1 — report so far

**Completed:** monorepo, `@solo/shared` (protocol envelope, task/action types, permission policy with guest isolation, model routing + budget check, memory types + secret screen), unit tests, architecture doc.
**Outstanding:** Dart mirror of shared contracts; Flutter design tokens/orb (Android still the default template); electron dev run not visually verified.
**Known limitations:** Dart contract mirror not yet generated. Policy shell deny-list is a backstop, not a sandbox; real safety is the closed action enum + confirmation.

## Phase 2 - report
**Completed:** wss link server (pinned self-signed cert, challenge/response auth, pairing window with lockout, revoke), device store, mDNS advertise, desktop shell (nav, Devices screen with pairing code, status dot), IPC bridge; Android shell (theme matching desktop, orb, Devices/Pair screens), Dart link client (TOFU + pin, reconnect backoff, secure token storage), mDNS discovery, shared proof vectors.
**Tests performed:** 11 desktop vitest tests using a real wss client (pair, reconnect with token, wrong code, no pairing window, MITM fingerprint, unknown/revoked, replay, pre-auth drop, cert stability); shared tests; Dart proof-vector tests (match the TS vectors) and a shell widget test; `tsc` and electron-vite build; the real Electron app launched and answered a TLS `auth.challenge` on :47821.
**Not tested:** Dart `LinkClient` against the real desktop (needs a device/emulator); mDNS discovery on a real network; Windows Firewall prompt; reconnect after Wi-Fi drop on hardware; desktop and phone UI visually (no screenshot review).
**Known limitations:** device tokens are plaintext on desktop disk; manual code/address entry (no QR); offline sync/conflict resolution not built yet; user login deferred to Phase 11 (Phase 2 authenticates devices only); no Android background service, so the link only runs while the app is open.
**Next:** Phase 3 - voice engine.

## Phase 2.1 - report (rename, auto-pair, background link)
**Completed:** rename for this PC, paired phones (desktop alias) and this phone; code-free pairing (`pair.ask`) with desktop approve/deny and 4-digit confirmation code; opt-in auto-approve on desktop and opt-in auto-ask on phone; mDNS discovery also tracks IP changes; Android foreground service hosts the link so it survives closing the app.
**Tests performed:** 10 new desktop tests (ask approve/deny/auto/disconnect/limits, rename, private-address check, SAS); Dart SAS vector + state serialization tests; desktop and Android analysis clean; Android release APK built (17.5 MB).
**Not tested:** installing/running the new APK (phone was not visible to adb); the foreground service on real hardware (Huawei background restrictions are expected to need the manual battery setting); mDNS discovery; auto-pair end to end.

## Phase 3 - report (voice engine)
**Completed:** voice settings, wake-phrase matcher ("Hey Solo"/"Hey Solomon", optional bare "Solo", mis-hearing aliases, wake word must lead the sentence), voice state machine (off/idle/listening/thinking/speaking; barge-in; follow-up window; nothing submitted while the mic is off; ambient speech dropped), energy-based utterance segmenter with pre-roll, resampler, local Whisper (tiny.en, q8) via transformers.js in the main process, Windows voices for speech output (voice/speed selectable), mic capture via AudioWorklet, mic permission gated by an in-app switch, Voice screen (mic switch, status orb, heard log, mic/voice/speed/follow-up settings).
**Tests performed:** 16 unit tests (wake matching, state machine, segmenter, resample); 2 cleanup tests; real-speech check with a Windows-synthesised WAV through Whisper in plain Node and inside Electron 33 (transcribed "Hey Solo, Open Chrome, and search for Dango documentation." and an ambient sentence; wake matcher woke on the first and ignored the second). First model load ~1 min including ~40 MB download, then ~3 s per utterance on this CPU.
**Not tested:** live microphone capture, echo-cancelled barge-in, device switching, speech output through the UI (needs a person at the PC; see TESTING.md).
**Known limitations:** wake word is detected by transcribing speech and matching text, not a dedicated openWakeWord/Porcupine model, so it costs CPU whenever someone speaks and may miss or false-trigger more than a trained detector (dedicated detector is a later upgrade); one utterance is transcribed at a time (speech during transcription is dropped); speaker selection follows the Windows default (Chromium speech synthesis cannot be routed per device); Piper TTS not integrated; no phone-side voice yet; spoken replies are an echo ("I heard: ...") until Phase 4.
**Next:** Phase 4 - conversational AI (OpenRouter).

## Phase 2.2 / 3.1 - report (sync, female voice, mic fix)
**Completed:** generic last-writer-wins sync engine (TypeScript and Dart, same semantics) with hybrid clock, full-state exchange on connect and live deltas, persistence on both sides; voice/assistant settings synced between PC and phone (phone Settings screen); Solo's voice defaults to female (Zira on this PC) and is selectable (female/male/default) with a per-PC specific-voice override; fixed the microphone failing with "The user aborted a request" (the audio worklet was inlined as a data: URL and blocked by the CSP; assets are no longer inlined).
**Tests performed:** 10 shared sync/voice-choice tests; 6 desktop sync integration tests over real wss (connect snapshot, phone-to-PC, relay to a second phone without echo, PC-to-phones, stale data rejected, persistence, malformed deltas dropped); 7 Dart sync tests mirroring the TS cases; all 12 Dart tests and 39 shared + 29 desktop tests pass; built output checked for data: URLs; Electron permission handler probed with a real `getUserMedia` call.
**Not tested:** the fixed microphone flow on your PC (the same call succeeds in a scratch Electron window here, but I have not heard it work in Solo itself); the new APK on the phone; sync phone-to-PC on real devices; spoken female voice by ear.
**Known limitations:** only settings sync so far (memories/tasks/conversations arrive with Phases 4-6); the phone does not speak yet, so voiceGender only affects the PC; sync is last-writer-wins per row (concurrent edits to different fields of the same row: the later write wins as a whole); no Piper voice yet.

## Phase 3.2 - report (wake words in the background, desktop tray, phone listener)
**Completed:** wake phrases ("Hey/Hi Solo", "Hey/Hi Solomon", bare "Solo"/"Solomon" by default) in shared TS and Kotlin with mirrored tests; desktop tray, hide-on-close, single instance, start-with-Windows (hidden), opt-in auto microphone, wake-word reveal of the window, settings card; phone foreground microphone service with offline two-stage wake detection, spoken replies without opening the app, listen switch with permission handling, recent-heard list, desktop-synced voice settings.
**Tests performed:** 42 shared tests (incl. new wake cases); 4 Kotlin JUnit tests on the wake matcher; 14 Dart tests (incl. listen UI and permission denial); desktop typecheck/build; live Windows check: closing the window keeps Solo and its link server running with the window hidden, relaunching brings the window forward.
**Not tested:** on-phone detection and TTS on real hardware (APK installation and a spoken test pending), phone reliability on Huawei background limits, the tray icon appearance, start-with-Windows after a real reboot, desktop wake-from-tray by actual speech.
**Known limitations:** a fully quit desktop app and a force-stopped phone app cannot listen; the phone listener cannot start at boot (Android 14+ rule) and must be switched on again after a restart; phone replies are an echo until Phase 4; no barge-in on the phone yet; phone wake uses the offline Vosk small model (accuracy is below a purpose-trained wake-word model); an extra ~41 MB in the APK.

## Phase 11a - report (internet access: relay, end-to-end encryption, many devices)
**Completed:** Solo relay server (`apps/relay`, deployable Dockerfile + README); device identity from Ed25519 keys (device id = hash of key) shared by LAN and relay; end-to-end session crypto (signed X25519 handshake, HKDF, AES-256-GCM) in TypeScript and Dart; pairing over the internet with a 12-character code; desktop `RelayClient` + `Hub` (LAN preferred, relay fallback); sync flooded across all connected devices so one phone with several laptops converges; Devices screen "Remote access" (relay address, status, show/enter pairing code); phone relay client, peer list with live status, relay address, "Pair over the internet"; relay address synced to every paired device; startup crypto self-test.
**Tests performed:** 13 crypto, 16 relay-server, 9 desktop relay-integration (code pairing, wrong/expired/reused code, lockout, one phone + three laptops converging and addressing, reconnect catch-up, strangers and revoked devices ignored, URL validation), 4+ Dart interop vectors matching TypeScript byte for byte, a cross-language Dart-phone to TypeScript-desktop test through the real relay (pair, ordered encrypted messages both ways), and a live run of the real desktop app over a local relay with a stand-in phone (set relay in the UI, show code, join, settings synced both directions, relay address propagated).
**Bug found only by live testing:** Electron's crypto has no ChaCha20-Poly1305 (BoringSSL), so remote messaging failed inside the app while unit tests (plain Node) passed; switched to AES-256-GCM and added a startup self-test that runs in the real runtime.
**Not tested:** a deployed relay on the real internet; the phone on mobile data (needs the new APK and a public relay); Docker image build (Docker is not installed here); two real PCs; relay behaviour under real mobile-network drops; battery impact of the always-on connection.
**Known limitations:** no offline message queue; no TURN yet (needed for call audio and screen mirroring over mobile networks in Phases 8-9); the phone keeps one LAN desktop plus any number of relay peers; a laptop paired only over the internet is reached through the relay (no LAN fast path); desktop and phone ids changed, so existing pairings must be redone once; relay free-tier terms unverified.

## Phase 12a - report (file synchronisation)
**Completed:** evaluation and decision (Syncthing engine driven by Solo; SYNC.md); engine supervision (hidden process, loopback API with key, telemetry and upgrades off, graceful stop, process-tree kill, lock retry after a crash, automatic restart); Solo layer (identity introduction between trusted devices, folder offer and accept into any local path, safe default exclusions, per-folder ignore editor, staggered version history, conflict list with Keep current / Use the other / Keep both, history browser with restore, status and progress, problem list, privacy switches); Files screen; hardened IPC (validated paths and ids); pinned engine fetch script.
**Tests performed:** 12 real-engine tests (two independent engine instances plus the Solo flow) all pass: both-way sync with rename/delete, exclusions (and package-lock.json still syncing), OFFLINE catch-up including an 8 MB file, CONFLICT preserving both versions on both devices, HISTORY archive and restore (restored version synced back), INTERRUPTED transfer (engine killed mid-transfer, restarted, SHA-256 identical), RECONCILIATION by periodic scan with the watcher off, API lock-down; 12 unit tests for ignore rules, conflict parsing/resolution, history restore and path-traversal refusal; protocol test for `files.device`. Live check of the Files screen in the real app (isolated profile, screenshot reviewed) and of input validation over IPC.
**Bugs found by testing and fixed:** (1) `stop()` returned before the process exited; (2) a hard kill left an orphaned worker holding the database lock (and syncing), so crash recovery failed: now the whole process tree is killed and restart retries the lock; (3) the LAN link server did not fall back to another port when its default was taken: the app hung instead (the busy-port error was unhandled), fixed with a regression test.
**NOT tested (important):** two real PCs on different internet connections (NAT traversal, discovery and relay fallback over the internet): loopback cannot exercise them; the manual checklist in TESTING.md must be run. The folder picker and clicking through the Files screen with real data; Windows firewall prompt behaviour; very large folders; Windows file locking by other programs; permission handling; long paths. Android is not covered.
**Known limitations:** Android phone folders are not synced (needs the separate Syncthing Android app or a future Android implementation); the engine uses its own discovery/relay network, not the Solo relay; exclusions skip a folder literally named `build` or `out` even in non-JS projects (editable per folder); `.git` is not synced by default; engine PGP signature not verified when pinned; the Syncthing binary adds about 14 MB and is not committed (fetch script).
**Note on an unexplained start:** during my UI checks a test window of Solo was visible on the PC and an engine was found running from one of those temporary profiles. Automated reproduction (same script, fresh profile) never started it and the setting is off by default, so it was most likely switched on by hand in that test window. It was stopped and the profiles deleted; the real profile has never enabled file sync.

## Phase 3.3 - report (owner's voice, Nigerian English, speech that breaks)
**Completed:** speaker verification with enrolment (5 sentences, consistency check, noise/speed augmentation), voice print stored locally and encrypted (never synced), owner-only mode, greetings without a wake word (English and Nigerian: "hello", "hi", "good morning/afternoon/evening/night", "how far", "how you dey"), owner-only interruption, "Test my voice" with live score and a strictness slider, Voice screen cards (My voice, Recognition accuracy); Nigerian English/Pidgin normaliser, coarse intent classifier, user-taught corrections ("Fix" in the heard log); selectable speech-recognition model size with automatic fallback; the microphone is ignored while Solo speaks (tested policy), echo replies no longer contain "Solo", replies are spoken sentence by sentence with utterances kept alive.
**Tests performed:** shared 74 (incl. owner-gating state machine, greetings, Nigerian normaliser, corrections, voice-print maths, mic policy); desktop VoiceId 10 (enrolment rules, mixed-person enrolment refused, encryption at rest, restart, deletion, wrong model ignored) and sentence splitting 3; real speaker model on real audio (opt-in): owner 11/12 and other voice 0/12 on unseen sentences, owner 4/4 in noise from 30 to 5 dB, 6/6 very fast speech, short greetings 2/3; speech model speed/WER for the fast model; live checks in the real app of the IPC (too-short/silent recordings rejected, bad input safe) and of the new screen cards.
**Measured improvement worth noting:** adding noise/speed copies to enrolment raised noisy-room owner acceptance from 1/4, 0/4, 0/4, 0/4 to 4/4 at every level and fast speech from 2/6 to 6/6, with no extra false accepts.
**NOT verified (important):** any real person's voice (the only "people" were the two Windows text-to-speech voices; accuracy for you is unknown); Nigerian-accented speech and Pidgin recognition (no such audio; the Better/Best models could not be downloaded here, so they have not been run at all); the cause of "breaks mid-talk" could not be reproduced acoustically (the Chromium garbage-collection hypothesis was tested and ruled out; the self-hearing hypothesis was fixed by design and unit-tested but not heard); the enrolment and test screens used by a person; interruption by voice with real speakers and microphone; spoofing resistance (none).
**Known limitations:** a bare one-second "Hello" can be missed; voice recognition is desktop-only (the phone's wake-word service is separate); Better/Best speech models are unproven; the Pidgin lexicon is a starter list, not an understanding of Pidgin; without a voice print there is no voice interruption (a Stop control in the app is the alternative).
